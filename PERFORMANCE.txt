original README install the official release, not this fork.

What changed

1. Validation strategy and task scope

The runtime does not automatically run an entire validation suite after an
edit. The model chooses shell commands, influenced by its system prompt,
repository instructions and skills. Removing a runtime delay alone cannot
fix a model repeatedly selecting expensive validation.

The stock prompts now share a workflow policy: answer ordinary discussion
directly, keep exploration proportional to the change, batch related edits,
use focused checks while iterating, run required checks at completion, and
reuse passing results until a relevant input changes. Required repository
checks still apply. Meta's prompt no longer demands delegation for ordinary
code exploration. The native Claude Agent SDK prompt receives the policy too.

This is model guidance, not a hard restriction on shell commands. Its effect
on real work has not been measured against a live model. A custom system
prompt on the standard route continues to override the stock system prompt.

2. Tool schema copying

Request preparation used to JSON-serialize and parse every tool input schema
before running context hooks. Built-in prompt hooks usually enumerate tool
names; they do not need those copies. Schemas are now copied lazily when a
hook reads them. Schema mutations remain isolated between requests, and
assignment and rename behavior is covered by regression tests.

3. Interrupted reasoning replay

For each reasoning block in an interrupted assistant response, replay used
to copy the remaining content array and scan it for later output. This was
quadratic in the number of blocks. It now finds the last output once and
does a linear pass. A regression test counts content reads instead of using
a timing threshold.

Other findings and boundaries

- Local tools already run concurrently, and the initial snapshot already
  overlaps the provider request. Those paths were retained.
- Every model step reloads durable history. This is a documented session
  invariant; replacing it with an in-memory loop would change recovery and
  steering behavior.
- The end snapshot is on the critical path. Large worktrees can make it
  expensive, but removing it would compromise change tracking and undo.
- Plugin readiness is awaited at step boundaries. Slow plugin activation or
  reload can therefore delay work; no blanket timeout or bypass was added.
- Automatic compaction can make another model request. Background summaries
  already reduce that wait. Their usefulness depends on context size.
- Provider generation, reasoning effort, tool execution and retries remain
  potential sources of seconds-long delays. Their relative contributions
  in live user sessions are unmeasured.

Existing tracing supports OTEL_EXPORTER_OTLP_ENDPOINT. Useful spans include
SessionRunner.drain, SessionRunner.prepareContext, SessionContext.load,
SessionModelRequest.prepare, SessionStep.attempt, LLM.stream and
Snapshot.capture. Compare these on an actual slow session before removing
additional behavior or reducing model effort.

Additional I/O improvements

4. Repeated failed PTY startup

Related upstream issue: https://github.com/anomalyco/opencode/issues/64080

An unsuccessful start was followed by another start from the request retry,
and every later request repeated that work. When an unreachable helper stays
alive without a working socket, this costs about twenty seconds per request.

Failed starts now have a thirty-second cooldown measured with the monotonic
Effect clock. Concurrent callers share that result under the existing
startup permit. Discovery still runs before the cooldown gate, so an already
recovered daemon can be used immediately. Successful recovery clears the
failure; cancellation is not cached. Ordinary direct-spawn fallback remains
available to shell commands. A repaired binary may wait until the cooldown
expires before another automatic launch attempt.

Controlled reproduction with the actual daemon transport and a helper that
registers an unreachable socket, measured once per build on this Mac:

Workload                               Baseline       Patched
First failed PTY request                20,088 ms      10,067 ms
Second failed PTY request               20,064 ms      <1 ms
Total helper launches after both calls      8             2

The initial recovery attempts still take time. This fixes repeated startup
work when the daemon is unavailable; it does not speed up a healthy provider
or establish that a particular user's environment has a daemon failure.

5. Uniform-line-ending edits

Related upstream issue: https://github.com/anomalyco/opencode/issues/60305

The edit tool used a full longest-common-subsequence table to preserve line
endings even when every ending was identical. The table is unnecessary for
uniform LF or CRLF regions: every possible alignment yields the same ending.
Those cases now use a linear replacement. Mixed-line-ending regions retain
the original alignment algorithm and can still have quadratic cost.

A one-line change supplied with 12,000 lines of LF matching context, executed
through the actual registered edit tool with formatting disabled, took 703 ms
on baseline and 14 ms with this fast path. Output equality was checked. The
baseline LCS table for this input requires about 576 MB of typed-array
storage; RSS is affected by garbage collection and is not used as a peak
memory measurement. These are single-run observations, not statistical
end-to-end task benchmarks.

Repeat these I/O reproductions without model credentials:

  cd packages/core
  bun run script/benchmark-loop.ts io

The PTY reproduction deliberately waits through startup timeouts, so the
patched benchmark takes about ten seconds. It creates isolated temporary
files and fixture helper processes. The PTY case currently runs on POSIX;
the daemon cooldown's deterministic tests also cover the retry boundary,
concurrent failures, cancellation, and recovery without waiting thirty
seconds. Large-region edit tests cover both LF and CRLF output.

6. Whitespace-tolerant edit matching

The fallback that matches oldString while ignoring trailing whitespace used
to copy a candidate line range at every position, repeatedly normalize the
same lines, and scan earlier matches for overlaps. Repeated source lines
and long search regions made this work quadratic.

Both source and search lines are now normalized once. KMP prefix matching
finds candidates in linear time, and a constant-time comparison with the
last accepted span preserves the first, non-overlapping matches. The span
comparison uses original string offsets; blank final lines can be shared
without overlapping the replaced text. Exact and typography-only matching
still take priority, and the line-ending preservation path is unchanged.

A 4,000-line file with repeated trailing whitespace and a 2,000-line search
pattern took 466 ms through the published edit tool (8de2cf7) and 10 ms
through the final candidate. The output was checked for equality. These are local
single-run observations; the new fast path applies when the whitespace-
tolerant fallback is needed.

Regression cases exercise partial-prefix fallback, repeated/overlapping
matches, empty final lines and CRLF output through the real registered
tool. A one-off differential experiment also compared the old and new
matching helpers over 19,857 generated and 262,320 exhaustive small cases;
all returned identical match spans. A large repeated-region regression
exercises the algorithm without asserting machine-dependent timings.

Repeat the edit benchmarks without waiting through the PTY failure case:

  cd packages/core
  bun run script/benchmark-loop.ts search
